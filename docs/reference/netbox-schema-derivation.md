# NetBox OpenAPI → layered MCP tools: schema derivation spec

Reconnaissance for replacing the 446-tool NetBox MCP server with five layered tools, where
layers 1 (object-type registry) and 2 (field/filter description) are **generated from the
connected instance's own `/api/schema/?format=json`**.

## 1. Fetching

### 1.1 Endpoint and authentication

**[V]** On `demo.netbox.dev`, `/api/` and `/api/status/` both return **403** to an
unauthenticated client, while `/api/schema/` returns a **non-error body**. That instance
therefore runs with `LOGIN_REQUIRED = True`, and the schema endpoint is _not_ behind the same
gate as the rest of the API.

**[V]** NetBox's API permission class is `IsAuthenticatedOrLoginNotRequired` — "Permits access
when authenticated or when `LOGIN_REQUIRED` configuration is disabled" — applied to the API
viewsets, and `StatusView` is described as "A read-only endpoint at `/api/status/`".

**[D]** drf-spectacular's `SpectacularAPIView` defaults to `SERVE_PERMISSIONS =
['rest_framework.permissions.AllowAny']`, and NetBox does not override it. That is consistent
with the 200/403 split observed above.

**[V — live 4.6.0]** A **bad** token is answered **403**, not 401, with
`{"detail":"Invalid v2 token"}`, and a request with **no** `Authorization` header is answered
403 with `{"detail":"Authentication credentials were not provided."}`. Both share a status
with a genuine permission refusal, so **the status alone cannot be mapped to advice** — the
`detail` string is the only thing that distinguishes "your token is wrong" from "your token
may not do this", and a body matching neither must be reported as ambiguous rather than
guessed at. See `src/errors.ts`.

**Recommendation (design, not a finding): always send the API token when fetching the schema
anyway.** The unauthenticated path works on stock NetBox but breaks under
`EXEMPT_VIEW_PERMISSIONS`/reverse-proxy auth, and sending the token costs nothing. Do **not**
build a "fetch schema without credentials" code path.

### 1.2 Content negotiation — this bit is a real trap

**[V]** `?format=json` does **not** yield `Content-Type: application/json`. drf-spectacular
serves the JSON rendering as **`application/vnd.oai.openapi+json`** (and the YAML rendering as
`application/vnd.oai.openapi`). This is exactly why the fetch above came back as
`[binary data]`: a client that switches on content-type saw an unknown vendor type and refused
to decode it.

Implications for the MCP server's HTTP client:

```
GET /api/schema/?format=json
Authorization: Token <token>
Accept: application/vnd.oai.openapi+json, application/json
Accept-Encoding: gzip
```

- Parse the body as JSON **regardless of the returned content-type** — do not gate on
  `content-type === 'application/json'`. [V, learned the hard way]
- Request gzip. **The document is 12.9 MB of JSON, not ~4 MB** (§1.3) — measured gzip -9 of
  `contrib/openapi.json` is 480,086 bytes ≈ 469 KB (27× ratio; the document is extremely repetitive). Gzip is
  not optional at this size. [V]
- Set a generous timeout: NetBox generates the schema **on every request** (there is a
  long-standing request to pre-generate it, netbox issue #6423 "Pre-generate the OpenAPI
  schema", still open). Generation on a large instance takes **seconds**. [V — issue exists]
- `?format=yaml` (the default) is smaller but needs a YAML parser; prefer JSON.

### 1.3 Document size

**[V]** The NetBox-maintained Go client vendors the generated spec at
`go-netbox/api/openapi.yaml` = **4.19 MB of YAML** (NetBox 4.3.0, measured on disk).

**[X] The ~4.5–5.2 MB JSON estimate was far too low.** Measured: NetBox 4.6.7's
`contrib/openapi.json` is **12,938,247 bytes ≈ 12.9 MB** — roughly **3× the earlier estimate**.
Two reasons: (a) the JSON is pretty-printed by `manage.py spectacular`, and (b) NetBox 4.4+
added the `oneOf` single-or-array POST bodies and `oneOf` integer-or-object FKs (§3.1, §3.4),
which materially inflate the document. At ~3.5 chars/token this is **≈ 3.7 million tokens**.
A live `?format=json` fetch is not pretty-printed and will be smaller — expect **6–9 MB** —
but budget for the worst case.

> **This document must never be placed in a model's context, in whole or in part-by-accident.**
> It is parsed server-side into a compact registry; only the compacted derivations of §2–§4
> are ever shown to a model.

### 1.4 Cache key

**[V]** `/api/status/` "delivers operational information, returning details like
`"netbox-version"`, `"django-version"`, `"python-version"`, installed apps, plugins, and
`"rq-workers-running"`."

**[V]** It requires authentication when `LOGIN_REQUIRED=True` (403 observed on the demo).

**Cache key recommendation:** `sha256(netbox-version + sorted(plugins map))`. The plugin list
matters as much as the core version — installing or upgrading a plugin changes `paths` without
changing `netbox-version`. `/api/status/` returns both in one authenticated call. [V for the
fields, design recommendation for the composition]

**[V] Caveat:** `netbox-version` is not universally reliable — netbox-docker issue #1582,
"v4.5.0-beta1 Docker image: `/api/status/` returns null for netbox-version and python-version".
Fall back to hashing the fetched schema document itself (cheap: hash while streaming) when
`netbox-version` is null.

## 2. Object-type registry (layer 1)

### 2.1 Path shapes

**[V]** Paths in the NetBox 4.x schema **include the `/api/` prefix**. From the drf-spectacular
migration PR (#11626), listing the breaking changes: paths changed from
`"/circuits/circuit-terminations/"` to `"/api/circuits/circuit-terminations/"`.

**[V]** Confirmed in the 4.6.7 document: **every one of the 308 paths starts with `/api/`** —
there are no non-`/api` keys at all, so the `segs[0] != 'api'` skip in §2.2 never fires. Keep
it as a defensive guard, not as a load-bearing branch.

**[I — still unverified, and now known to be unverifiable from this document]** Plugin
endpoints follow `/api/plugins/<plugin-name>/<model-name>/`. NetBox's plugin
development docs: _"This will make the plugin's view accessible at
`/api/plugins/my-plugin/my-model/`"_, produced by `router = NetBoxRouter(); router.register('my-model', MyModelViewSet)`.
**`/api/plugins/` appears zero times in the stock 4.6.7 schema**, because NetBox generates
`contrib/openapi.json` from an instance with no plugins installed. See Risk 17.

### 2.2 The collection/detail rule

Classify each key of `paths` by **segment count after `/api`**, not by regex-matching `{id}`
alone:

```
segs = path.strip('/').split('/')          # e.g. ['api','dcim','devices']
if segs[0] != 'api': skip                  # nothing else is served under /api
plugin = (segs[1] == 'plugins')
base   = segs[2:] if plugin else segs[1:]  # ['devices'] / ['dcim','devices'] etc.

core collection : len(segs)==3 and no '{'          → /api/dcim/devices/
core detail     : len(segs)==4 and segs[3]=='{id}' → /api/dcim/devices/{id}/
plugin coll.    : len(segs)==4 and no '{'          → /api/plugins/foo/bars/
plugin detail   : len(segs)==5 and segs[4]=='{id}' → /api/plugins/foo/bars/{id}/
anything else   : sub-resource / action endpoint, NOT an object type
```

**[V] Measured against NetBox 4.6.7 (308 paths). The segment-count rule holds, with an exact
census:**

| Bucket                                                      | Count            |
| ----------------------------------------------------------- | ---------------- |
| 3-segment core **collection** paths (`/api/<app>/<slug>/`)  | **138**          |
| 4-segment core **detail** paths (`/api/<app>/<slug>/{id}/`) | **133**          |
| Everything else under `/api/`                               | **37**           |
| Paths not under `/api/`                                     | **0**            |
| Plugin paths (`/api/plugins/**`)                            | **0** — see §2.7 |

**No path violated the segment-count classification.** There were no surprises like a
5-segment collection or a detail path keyed on something other than `{id}` _inside the
collection/detail buckets_. Every anomaly landed in "everything else", which is what you want.

**[X] The guard as written is not sufficient.** "Only emit an object type when a collection
path with a `get` exists" admits 12 non-types. **All 138 collections have a `get`; zero are
discarded by that guard.** The rule that actually works is **`post` on the collection AND a
matching `/{id}/` detail path**, which yields **126 object types** and excludes exactly these
**12**:

```
/api/core/background-queues/     GET only, no detail path      (viewset has no serializer)
/api/core/background-workers/    GET only, no detail path      (viewset has no serializer)
/api/core/background-tasks/      GET, detail exists, no POST
/api/core/data-files/            GET, detail exists, no POST   (read-only, synced from a DataSource)
/api/core/jobs/                  GET, detail exists, no POST   (read-only)
/api/core/object-changes/        GET, detail exists, no POST   (read-only changelog)
/api/core/object-types/          GET, detail exists, no POST   (read-only content-type registry)
/api/dcim/cable-terminations/    GET, detail exists, no POST   (read-only projection of Cable)
/api/dcim/connected-device/      GET only, no detail path      (query endpoint — netbox #12682)
/api/extras/tagged-objects/      GET, detail exists, no POST   (read-only)
/api/users/config/               GET only, no detail path      (singleton: the caller's UI config)
/api/extras/dashboard/           GET/PUT/PATCH/DELETE, no detail path — SINGLETON, NOT BULK
```

`/api/extras/dashboard/` is the nastiest of these and is **new information** — see §2.4 and
Risk 4.

The 37 "everything else" paths are enumerated in §2.7. They break down as: 24 sub-resource
actions on detail paths (`.../{id}/trace/`, `.../{id}/paths/`, `.../{id}/sync/`,
`.../{id}/available-ips/`, `/api/dcim/racks/{id}/elevation/`,
`/api/dcim/devices/{id}/render-config/`, …), 6 background-task actions, 2 `{name}`-keyed

### 2.3 Deriving the `object_type` key

Target form is NetBox's own canonical `app_label.model_name`, e.g. `dcim.device`.

```
app  = segs[1]                            # 'dcim'          (plugins: 'plugins.<plugin>')
slug = segs[2]                            # 'ip-addresses'
model = singularise(slug.replace('-',''))  # 'ipaddresses' -> 'ipaddress'
object_type = f"{app}.{model}"             # 'ipam.ipaddress'
```

Singularisation rules needed, from the 82 real endpoint slugs present in the current
hand-written server (`/home/claude/work/netbox-mcp-server/src/tools/*.ts`) [V — read from the repo]:

| Slug                            | Naive `-s` strip         | Correct                                                   |
| ------------------------------- | ------------------------ | --------------------------------------------------------- |
| `ip-addresses`, `mac-addresses` | `ipaddresse`             | `ipaddress` (`-es` after `s`,`x`,`z`,`ch`,`sh`)           |
| `purchases` (netbox-inventory)  | `purchase` ✓             | `purchase` — **but the `-es` rule above gets this WRONG** |
| `prefixes`                      | `prefixe`                | `prefix`                                                  |
| `vlan-translation-policies`     | `vlantranslationpolicie` | `vlantranslationpolicy` (`-ies` → `-y`)                   |
| `rirs`, `asns`, `vrfs`, `vlans` | ✓                        | ✓ (plain `-s`)                                            |
| `console-server-ports`          | ✓                        | `consoleserverport`                                       |
| `device-bays`                   | ✓                        | `devicebay`                                               |

**[V — live 4.6.0] `-ses` is ambiguous and "strip `-es` after a sibilant" is not sufficient.**
`plugins/inventory/purchases` derived as `plugins.inventory.purchas`. The singular of a `-ses`
plural ends in `-s` only when it is itself sibilant-final (`address`, `status`, `bus`);
otherwise the plural was formed on a silent `-e` (`purchase`, `license`, `case`) and only the
`-s` comes off. Test the CANDIDATE, not the plural: strip `-es`, and keep that result only if
it ends in `ss`/`us`/`is`. `-xes`/`-zes`/`-ches`/`-shes` carry no such ambiguity.

**Better still, do not derive the model from the slug when the schema already named it.** The
request/response component resolved for the endpoint (`PurchaseRequest` → `Purchase`) is the
serializer's own name for the model and is authoritative; the slug is a routing convenience.
Use the component where it agrees with the slug modulo pluralisation, and fall back to the
heuristic where it does not — which is exactly the set of endpoints named below, where the
component is not the URL's noun. See `modelNameFor` in `src/schema/registry.ts`.

**[V] This mapping is lossy for a handful of endpoints where the URL slug is not the model
name.** Confirmed in 4.6.7: `/api/users/permissions/` resolves to read component
`ObjectPermission` and write component `ObjectPermissionRequest`, so the path rule yields
`users.permission` while NetBox's own object-type string is `users.objectpermission`.
`/api/extras/tagged-objects/` → `TaggedItem`. `/api/virtualization/interfaces/` →
`VMInterface`. `/api/dcim/virtual-chassis/` is already singular in the URL (naive
de-pluralisation would mangle it). **Do not claim your derived key equals Django's
`app_label.model_name`.** Two options, in order of preference:

1. **Treat the derived key as your own stable identifier** and never cross-reference it with
   NetBox's `object_type` strings (which appear in `extras/*`, `core/object-changes`, GraphQL,
   and custom-field `object_types`). Simplest, no runtime dependency.
2. **Enrich at build time** from `GET /api/extras/object-types/`, which returns `app_label` +
   `model` + `display` for every registered model, and reconcile by fuzzy-matching the
   de-hyphenated slug. This also gives you the human-readable label you otherwise lack (§2.6).

### 2.4 Which verbs a type supports — and the bulk-operation trap

Read the **operation keys** on the two path items:

| Operation | Path       | Method                           | Notes |
| --------- | ---------- | -------------------------------- | ----- |
| `list`    | collection | `get`                            |       |
| `create`  | collection | `post`                           |       |
| `get`     | detail     | `get`                            |       |
| `update`  | detail     | `put` (full) / `patch` (partial) |       |
| `delete`  | detail     | `delete`                         |       |

**[V] CONFIRMED, and the exact numbers are:** of 138 collection paths,

| Collection method set                                                        | Count   |
| ---------------------------------------------------------------------------- | ------- |
| `GET POST PUT PATCH DELETE` (list + create + the three bulk ops)             | **125** |
| `GET` only                                                                   | **11**  |
| `GET POST` (no bulk — `/api/extras/scripts/`)                                | **1**   |
| `GET PUT PATCH DELETE` (**singleton**, no create — `/api/extras/dashboard/`) | **1**   |

and of 133 detail paths: 126 have `GET PUT PATCH DELETE`, 7 have `GET` only.

**Do not read `put`/`patch`/`delete` on the _collection_ path as create/update/delete.**
Verified for `/api/dcim/sites/`:

```
put    dcim_sites_bulk_update          body = array of BulkSiteRequest        (id required)
patch  dcim_sites_bulk_partial_update  body = array of PatchedBulkSiteRequest
delete dcim_sites_bulk_destroy         body = array of SiteRequest
```

`BulkSiteRequest.required = ["id","name","slug"]` — the `id` is what makes it a bulk op. Note
also that **bulk DELETE has a request body**, which most HTTP clients do not send by default.

**[V] NEW — the inverse trap.** `/api/extras/dashboard/` is a 3-segment collection path whose
`PUT`/`PATCH`/`DELETE` are `extras_dashboard_update` / `extras_dashboard_partial_update` /
`extras_dashboard_destroy` — **singleton operations on the calling user's dashboard, taking a
single `DashboardRequest` object, not an array**. So you cannot simply hard-code
"collection PUT ⇒ bulk". You must read the `operationId` suffix (`_bulk_update` vs `_update`)
**or** check whether the request body is `type: array`. The request-body shape is the more
robust signal; the `operationId` suffix is a cheap cross-check.

This is otherwise a gift for the layered design: bulk create/update/delete are free, and layer
3 can expose them as an array form of the same tool. But naive verb detection will mislabel
them in both directions.

### 2.5 `operationId` and `tags` vs the path string

**[V — drf-spectacular source]** `get_tags()` is:

```python
def get_tags(self) -> List[str]:
    tokenized_path = self._tokenize_path()
    return tokenized_path[:1]
```

i.e. **`tags` is only the first path token** — the app label (`dcim`, `ipam`, …). It carries no
model information. Useless as a type key; useful as a grouping facet for the registry.

**[V — drf-spectacular source]** `get_operation_id()`:

```python
def get_operation_id(self) -> str:
    tokenized_path = self._tokenize_path()
    tokenized_path = [t.replace('-', '_') for t in tokenized_path]
    if self.method == 'GET' and self._is_list_view():
        action = 'list'
    else:
        action = self.method_mapping[self.method.lower()]
    ...
    return '_'.join(tokenized_path + [action])       # OPERATION_ID_METHOD_POSITION='POST' (default)
```

So `operationId` is `<app>_<slug_with_underscores>_<action>`, e.g. **`dcim_devices_list`**,
`dcim_devices_create`, `dcim_devices_retrieve`. **[V]** Real NetBox operationIds of exactly this
shape appear in the schema-generation log quoted in netbox issue #20365:
`core_background_queues_retrieve`, `core_background_tasks_retrieve`,
`core_background_workers_retrieve`.

**[V] `tags` confirmed to be the app label only** — the complete tag set across all 1196
operations in 4.6.7 is exactly
`dcim(418) extras(183) ipam(172) circuits(101) vpn(90) virtualization(64) users(56)
tenancy(54) core(28) wireless(27) authentication-check(1) schema(1) status(1)`.
Thirteen values, no model information. Useless as a type key.

**Verdict: the path string is the more reliable source.** Reasons:

1. `operationId` is _computed from the path_, so it can never contain more information. [V]
2. It is **lossy**: `-` → `_`, so `console-server-ports` and a hypothetical `console_server_ports`
   collapse to the same token. [V]
3. **[X] The collision claim no longer holds at 4.6.7.** Measured: **zero duplicate
   `operationId`s across all 1196 operations, and zero `_2`/`_3` suffixes.** NetBox PR #20407
   added explicit `operation_id`s and fixed the `core_background_*` collisions reported in issue
   #20365. The historical warning stands as a reason not to _depend_ on operationId stability
   across versions — but it is no longer an active defect, and the trailing action token is a
   reliable cross-check today.
4. `tags` gives the app only. [V]

Use the path as the key; use `operationId`'s trailing action token (`_list` / `_create` /
`_retrieve` / `_update` / `_partial_update` / `_destroy` / `_bulk_*`) as a **cross-check** on the
verb classification in §2.4, and log a warning on disagreement.

### 2.6 Human-readable one-line description — better than expected, but only a label

**[X] Partially refuted, in your favour.** Measured on 4.6.7:

- **Operation `description` is present on 1196 / 1196 operations (100 %).** But it is
  templated, not prose: `"Get a list of Circuit group assignment objects."`,
  `"Post a list of Circuit group assignment objects."`, `"Delete a list of site objects."`
  The one non-templated example is `/api/authentication-check/`:
  _"Return the user making the request, if authenticated successfully."_

  **This is worth exploiting.** The template embeds NetBox's own **verbose model name**, so
  `paths[coll].get.description` gives you a free human label for every type — including
  plugins — with a one-line regex (`^Get a list of (.+) objects\.$`). That is strictly better
  than title-casing the slug, and it correctly renders `users.permission` as
  _"object permission"_ and `virtualization.interfaces` as _"VM interface"_. Use it as the
  generated fallback label.

- **Component `description` is present on 886 / 1043 schemas but is nearly worthless.** It is
  the serializer docstring, and the top five values are boilerplate repeated hundreds of times:
  _"Base serializer class for models inheriting from PrimaryModel."_ (×349), the
  `full_clean()` note (×131), _"Adds an `owner` field for models which have a ForeignKey to
  users.Owner."_ (×131), _"Base serializer class for models inheriting from
  OrganizationalModel."_ (×103), empty (×157). **Never surface this to a model.**

- **[V] Per-field descriptions are present and genuinely useful** — from Django model
  `help_text`. Real example, `WritableSiteRequest`: `name` → _"Full name of the site"_,
  `facility` → _"Local facility ID or description"_, `physical_address` → _"Physical location
  of the building"_, `latitude` → _"GPS coordinate in decimal format (xx.yyyyyy)"_. About half
  the fields have one; `slug`, `region`, `group`, `tenant`, `tags`, `custom_fields` do not.

- **[V] Enum fields carry a free value glossary** in their `description`:
  `"* \`offline\` - Offline\n* \`active\` - Active\n…"`. Confirmed on
`WritableDeviceWithConfigContextRequest.status`and on filter parameters such as`airflow`.

**Conclusion: the schema supplies a decent _label_ per object type but no _semantics_.**
"Device" does not tell a model when to reach for a device instead of a virtual machine. Fill
the gap in this order:

1. **Parse the operation-description template** for the verbose name. Free, covers plugins,
   no extra request. **This is a new, cheap win.**
2. `GET /api/extras/object-types/` → `display` (e.g. "DCIM > Device"). Adds app grouping.
   [I — still unconfirmed against a live instance; the schema's `ObjectType` component confirms
   the endpoint exists and is read-only.]
3. A small curated table for the ~40 types an agent actually reaches for, merged over the
   generated registry. Still the only way to say _"a device is a physical piece of hardware
   installed in a rack at a site"_. **Still recommended**, but now needed only for the top
   types, not as the entire labelling strategy.

### 2.7 Paths that are NOT object types — the complete 4.6.7 list

**[V]** The registry must exclude all of these. This is the full enumeration; a hand-wave here
is a runtime bug.

#### The verdict on name-mapping: worse than the recon pass claimed

**[V] CONFIRMED and ESCALATED.** Of the 126 object types:

- **65 have a write schema whose name is `Writable<Serializer>Request`** — a _majority-adjacent_
  fraction, not a handful. Full list in the analysis; it includes `dcim.site`
  (`WritableSiteRequest`), `dcim.rack`, `dcim.interface`, `ipam.prefix`
  (`WritablePrefixRequest`), `ipam.ipaddress` (`WritableIPAddressRequest`), `ipam.vlan`,
  `virtualization.cluster`, all of `vpn.*` and `wireless.*`, and `dcim.device`
  (`WritableDeviceWithConfigContextRequest`).
- **61 use the plain `<Serializer>Request` form** (`ManufacturerRequest`, `TenantRequest`, …).
- **The write schema name differs from `<ReadSchema>Request` for exactly those 65.**
- **The read schema name differs from the model name** for at least
  `dcim.device` → `DeviceWithConfigContext`,
  `virtualization.virtualmachine` → `VirtualMachineWithConfigContext`,
  `virtualization.interfaces` → `VMInterface`,
  `users.permission` → `ObjectPermission`,
  `extras.tagged-objects` → `TaggedItem`.

**[X] AND IT IS WORSE THAN "THE NAME IS MISSING". THE NAME IS OFTEN PRESENT AND WRONG.**

`SiteRequest` **exists** as a component — it is the **bulk-DELETE payload schema**, not the
create schema. `dcim/sites` uses `WritableSiteRequest` for POST and `SiteRequest` for
`DELETE /api/dcim/sites/`. A name-mapping rule `dcim.site → SiteRequest` would not throw; it
would silently resolve to the delete payload. For `dcim.device` the analogous
`DeviceWithConfigContextRequest` also exists (bulk-delete payload) while `DeviceRequest` does
not exist at all — so the same rule fails _loudly_ for devices and _silently_ for sites. The
loud failure is the lucky case.

And the two are **not interchangeable**: of the 65 `Writable*Request` / `*Request` pairs,
**46 differ** from their plain counterpart. The differences are subtle — enum member ordering,
and in 8 cases a differing `required` list
(`WritableCustomFieldRequest` requires `type` where `CustomFieldRequest` does not; likewise
`action_type` on event rules, `version` on IKE policies, `type` on L2VPNs, `form_factor` on
rack types, `protocol` on services and service templates, `status` on tunnels, `role` on
tunnel terminations). Only 19 pairs are byte-identical. **A name-mapping bug here produces a
schema that is right 95 % of the time and wrong on required-field validation — the worst
possible failure mode.**

> **Therefore: never build a name-based type→schema mapping. Resolve by `$ref` from the
> operation. This is now the single most load-bearing rule in the spec.**

#### **[X] The pointer walk in the previous revision is WRONG for NetBox 4.4+**

POST request bodies are no longer a bare `$ref`. Since NetBox #20638 they are a **`oneOf` of
[single object, array of objects]** so that one endpoint documents both single and bulk create.
Verified on `/api/dcim/sites/`:

```json
"post": { "requestBody": { "content": { "application/json": { "schema": {
  "oneOf": [
    { "$ref": "#/components/schemas/WritableSiteRequest" },
    { "type": "array", "items": { "$ref": "#/components/schemas/WritableSiteRequest" } }
  ] } } } } }
```

125 of the 126 object types have this shape. Upstream has a regression test for it
(`netbox/core/tests/test_openapi_schema.py::test_post_operation_documents_single_or_array`),
so it is deliberate and will persist. **A naive `post.requestBody…schema.$ref` lookup returns
`undefined` for every single object type in NetBox ≥ 4.4.**

The corrected walk:

```
def single_ref(schema):
    if 'oneOf' in schema: return single_ref(schema['oneOf'][0])   # [0] is the single form
    return schema.get('$ref')

write_schema(type)  = deref(single_ref( paths[coll].post.requestBody.content['application/json'].schema ))
patch_schema(type)  = deref( paths[detail].patch.requestBody.content['application/json'].schema.$ref )   # plain $ref
read_schema(type)   = deref( paths[detail].get.responses['200'].content['application/json'].schema.$ref ) # plain $ref
list_page_schema    = deref( paths[coll].get.responses['200'].content['application/json'].schema.$ref )   # Paginated<X>List
list_item_schema    = deref( list_page_schema.properties.results.items.$ref )
```

Notes, all measured:

- The detail `put` body **is** a plain `$ref` to the same write schema; only the collection
  `post` is wrapped in `oneOf`. Do not apply the unwrapper blindly — but making it idempotent
  costs nothing.
- The detail `patch` body is always `Patched<WriteSchemaName>` — **126/126, no exceptions**,
  e.g. `PatchedWritableDeviceWithConfigContextRequest`. It has **no `required` key at all**,
  as documented.
- The collection `get` 200 response is a **named `Paginated<X>List` component**, not an inline
  object. Two derefs to reach the item schema.
- **[V] Exception you must handle:** `/api/extras/scripts/` has a `POST` with **no
  `application/json` content at all** — `single_ref` returns `None`. It is 1 of 126. Treat a
  missing write schema as "create-unavailable", not as a crash.
- `multipart/form-data` is offered alongside `application/json` on every write operation with
  the same schema. Ignore it.

This is version-proof, plugin-proof, and immune to every naming quirk above _provided_ you
unwrap `oneOf`. Component names are then only useful as a **reverse index** (§3.4).

### 3.2 Required fields

`components.schemas.<WriteSchema>.required: [...]` — a plain array of property names. **[V]**

Real examples measured at 4.6.7 — note how short these are:

```

WritableSiteRequest.required                    = ["name", "slug"]                  (18 properties)
WritablePrefixRequest.required                  = ["prefix"]                        (15 properties)
WritableIPAddressRequest.required               = ["address"]                       (…)
BulkSiteRequest.required                        = ["id", "name", "slug"]
PatchedWritableDeviceWithConfigContextRequest   — no `required` key at all
```

Corrections to the previous revision:

- **[X] Read-only properties ARE in `required` on response components.**
  `COMPONENT_NO_READ_ONLY_REQUIRED` is **not set** in NetBox 4.6.7's `SPECTACULAR_SETTINGS`
  (PR #11626 set it at 4.0; it has since been removed). Measured:
  `DeviceWithConfigContext.required` contains `id`, `url`, `display`, `display_url`, `created`,
  `last_updated`, `config_context`, `parent_device`, `primary_ip`, and all nine `*_count`
  fields — 22 entries, most of them read-only. **`required` on a response component means
  "always present in the response", not "you must supply it".** Do not read a response
  component's `required` as create-required; it is only meaningful on the _write_ component.
  This is exactly the confusion `go-netbox`'s `fix-spec.py` exists to paper over.
- **[V] The `Patched*Request` component has no `required` array at all** — confirmed on
  `PatchedWritableDeviceWithConfigContextRequest`. Use it directly as the update tool's schema.

**[V] Caveat confirmed:** NetBox fields with a non-null default (`status`, `airflow`, `face`)
are absent from `required` but carry an inline `enum` and a description glossary. Layer 2
should surface the enum and any `default` alongside `required` so the model can distinguish
"you must supply this" from "there is a sane default". Note that drf-spectacular does **not**
emit `default` for these — the default lives only in the Django model, so the schema cannot
tell you which enum member is the default. Curate that for the top types.

### 3.3 Read-only fields

Two distinct markers, and you need both. **Both now [V].**

1. **`readOnly: true`** as a sibling key on a property of the **response** component. There are
   **1430 such properties** across the document. Real example — `DeviceWithConfigContext`:

   ```json
   "id":  { "type": "integer", "readOnly": true },
   "url": { "type": "string", "format": "uri", "readOnly": true }
   ```

   Its complete read-only set is: `id`, `url`, `display_url`, `display`, `parent_device`,
   `primary_ip`, `config_context`, `created`, `last_updated`, and the nine
   `console_port_count` / `console_server_port_count` / `power_port_count` /
   `power_outlet_count` / `interface_count` / `front_port_count` / `rear_port_count` /
   `device_bay_count` / `module_bay_count` / `inventory_item_count` fields — 19 of 49
   properties.

2. **Absence from the request component.** **[V] Confirmed exhaustively: zero of the 159+65
   `*Request` components contain a single `readOnly` property.** drf-spectacular strips them
   entirely under `COMPONENT_SPLIT_REQUEST`. `DeviceWithConfigContext` has 49 properties;
   `WritableDeviceWithConfigContextRequest` has 30.

So for a _create_ description you do not need to filter read-only fields at all — the write
schema is already the writable set. `readOnly` matters when describing what a **read** returns,
and for explaining to an agent why a field it saw in a `get` response is rejected on create.

**[V] Sharp edge:** drf-spectacular deliberately pops `readOnly` in relation contexts
(`schema.pop('readOnly', None)` inside `_map_serializer_field`), so a nested/FK sub-schema may
lack the flag even where the parent field is effectively read-only. Trust the request/response
split over the flag.

### 3.4 Foreign keys — the single most valuable derivation

This is what lets the server tell an agent _"you must create a site before a device."_

**[X] REFUTED — and this is the best news in the whole re-verification.** The claim that "the
schema lies about foreign keys" was true at NetBox 4.1.3 (issue #17709) but **PR #18451 landed
and the schema is now honest.** In 4.6.7, FK write properties are a `oneOf` of integer PK and
nested brief object. Measured on `WritableDeviceWithConfigContextRequest`:

```json
"site":        { "oneOf": [ {"type":"integer"}, {"$ref":"#/components/schemas/BriefSiteRequest"} ] },
"device_type": { "oneOf": [ {"type":"integer"}, {"$ref":"#/components/schemas/BriefDeviceTypeRequest"} ] },
"role":        { "oneOf": [ {"type":"integer"}, {"$ref":"#/components/schemas/BriefDeviceRoleRequest"} ] },

"tenant":      { "oneOf": [ {"type":"integer"},
                            {"allOf":[{"$ref":"#/components/schemas/BriefTenantRequest"}],
                             "nullable": true} ],
                 "nullable": true },
"primary_ip4": { "oneOf": [ {"type":"integer"},
                            {"allOf":[{"$ref":"#/components/schemas/BriefIPAddressRequest"}],
                             "nullable": true} ],
                 "nullable": true }
```

**Census across every `*Request` component: 1329 properties have the `integer | Brief*Request`
`oneOf` shape; 463 are `type: array` of `$ref`; 61 are some other `oneOf`; and there are
ZERO bare `$ref`-to-`Brief*Request` FK properties.** The nested-object-only form is gone.

**Corrected detection rule** [V]:

```
single FK   : prop.oneOf contains {'type':'integer'} AND a member resolving to Brief<X>Request
              (the object member is wrapped in allOf + nullable:true when the FK is optional;
               the outer prop then also carries nullable:true)
to-many FK  : prop.type == 'array' and prop.items.$ref == '.../Brief<X>Request'
tags        : prop.type == 'array' and prop.items.$ref == '.../NestedTagRequest'   (special-cased)
custom_fields: {'type':'object','additionalProperties':{}}                          (opaque; pass through)
target type : reverse_index[ '<X>' ]          # 'Site' -> 'dcim.site'
```

Note the FK **read** shape is different and simpler: `DeviceWithConfigContext.site` is a bare
`{"$ref": ".../BriefSite"}` (no `oneOf`, no integer). Read and write FK shapes must be
described separately.

Build `reverse_index` in layer 1 by walking every collection path once and recording, for each
object type, the component names reachable from its read schema **and** its `Brief*` form. The
`Brief*` names are the clean ones — `BriefSite`, `BriefDeviceType`, `BriefManufacturer` map
1:1 to model names, unlike the full read component (`DeviceWithConfigContext`). Strip the
`Brief` prefix and `Request` suffix, lowercase, and match against the model half of your
`object_type` keys.

**[V] Runtime behaviour and schema now agree.** NetBox's documentation states: _"When
performing write API actions (POST, PUT, and PATCH), related objects may be specified by either
numeric ID (primary key) or by a set of attributes sufficiently unique to return the desired
object."_ The **existing 446-tool server in this repo sends plain integers**
(`region: z.number().int()`, `tenant: z.number().int()` in
`/home/claude/work/netbox-mcp-server/src/tools/dcim.ts`) and works. **[V]** As of 4.6.7 the
schema documents that integer form explicitly, so the derived tool schema and the working
hand-written server agree without post-processing.

**Design consequence, unchanged but now cheaper:** layer 2 should present an FK as
`site: integer (id) | {name|slug: string} — references dcim.site (create one first if absent)`.
You no longer need a _corrective_ post-process, only a _simplifying_ one: collapse the two-member
`oneOf` into that one-line description rather than emitting the raw union. **Do keep the
collapse idempotent and do keep it working against a bare `Brief*Request` ref**, because
instances on NetBox ≤ 4.3 still emit the nested-only form.

### 3.5 Enums

**[X] Enums are NOT hoisted into named components.** NetBox sets
`'POSTPROCESSING_HOOKS': []`, which disables drf-spectacular's
`postprocess_schema_enums` hook. Measured: **zero components whose name ends in `Enum`.**
Enums are inlined at every use site, with `x-spec-enum-id` appearing **1920 times**. Real
example, `WritableDeviceWithConfigContextRequest.status`:

```json

  "enum": [
    "offline",
    "active",
    "planned",
    "staged",
    "failed",
    "inventory",
    "decommissioning"
  ],
  "type": "string",
  "description": "* `offline` - Offline\n* `active` - Active\n* `planned` - Planned\n…"
}
```

This is **simpler than expected**: no deref needed, read `prop.enum` directly. The
`description` glossary is free and worth surfacing verbatim.

**[X] The `Type666Enum` / `Type2fcEnum` name-collision risk is therefore MOOT at 4.6.7** —
there are no enum component names to collide. Issue #12149 was resolved by disabling the hook
rather than by fixing the naming. Nothing to key off, so nothing to get wrong. (Still: never
write code that _expects_ `$ref`-to-`*Enum`; it will produce nothing on 4.4+.)

**[V] Response/request asymmetry CONFIRMED — and it is worse than "value/label".** The read
form is a nested object carrying **two parallel enums**. `DeviceWithConfigContext.status`:

```json
{ "type": "object",
  "properties": {
    "value": { "enum": ["offline","active",…], "type":"string", "x-spec-enum-id":"65feb4244cc9110c",
               "description": "* `offline` - Offline\n…" },
    "label": { "type": "string", "enum": ["Offline","Active","Planned","Staged","Failed",…] } } }
```

The write form is the bare string. Layer 2 **must** describe the write form for create/update
and the read form when explaining output, or agents will echo back `{"value": …}` on update and
get a 400. Detection rule: a read property that is
`type: object` with exactly the properties `{value, label}` is a choice field; flatten it to
`value`'s enum when summarising, and say so.

**[V] Filter parameters use the write (bare-string) form**, e.g. the `airflow` parameter on
`GET /api/dcim/devices/` is `{"type":"string","nullable":true,"enum":[…]}` with the glossary in
`description`. Note the enum on nullable filters includes the **string** `"null"` as a member.

## 4. Filters

### 4.1 Where they live

**[V] CONFIRMED.** Query parameters live on the **operation** object, not the path item:
`paths['/api/dcim/devices/'].get.parameters`. **`paths[...].parameters` is `undefined` on every
collection path** — do not bother checking it. Each entry is
`{in: 'query', name, schema, description?}`; `required` is omitted (all filters are optional).
Real entry:

```json
{ "in": "query", "name": "airflow",
  "schema": { "type": "string", "x-spec-enum-id": "11cb3d363b41ba9e", "nullable": true,
              "enum": ["bottom-to-top","front-to-rear",…,"null",…] },
  "description": "* `front-to-rear` - Front to rear\n* `rear-to-front` - Rear to front\n…" }
```

### 4.2 How many, and why

**[V]** NetBox multiplies each filter by its lookup expressions. From NetBox's own filtering
reference:

- **Numeric fields** (ASN, VLAN ID, …): `__n`, `__lt`, `__lte`, `__gt`, `__gte` → **6 variants**
  including the base.
- **String/char fields** (name, address, …): `__n`, `__ic`, `__nic`, `__isw`, `__nisw`, `__iew`,
  `__niew`, `__ie`, `__nie`, `__empty` → **11 variants** including the base.
- **Foreign keys and others**: _"support just the negation expression: `n`"_ → **2 variants**,
  and NetBox conventionally exposes both a slug form (`site`) and an id form (`site_id`), each
  with its `__n` → **4 parameters per FK**.

**[V] MEASURED at NetBox 4.6.7. The ~300–330 estimate was slightly low but the right order of
magnitude; it is CONFIRMED, corrected to 342.**

| ----------------------------- | ---------------------- | ------------- | ---------- | ---- |
| `GET /api/dcim/devices/`      | **342**                | **248**       | **72.5 %** | 94   |
| `GET /api/dcim/sites/`        | 163                    | 122           | 74.8 %     | 41   |
| `GET /api/ipam/prefixes/`     | 158                    | 99            | 62.7 %     | 59   |
| `GET /api/ipam/ip-addresses/` | 153                    | 99            | 64.7 %     | 54   |

The widest endpoint in the whole document is **`GET /api/dcim/interfaces/` at 361 parameters**;
then devices (342), racks (291), device-types (249), virtual-machines (224), power-outlets
(220), custom-fields (210), inventory-items (210), rack-types (204), power-feeds (202).
**Across all GET operations the document contains 15,832 query parameters.**

### 4.3 Summarisation rule

Dumping the array is not viable (§5). Rule, in priority order:

1. **Always surface** the control set: `q`, `limit`, `offset`, `ordering`, `brief`, `id`.
2. **Surface every parameter with no `__` lookup suffix.** This is the base filter set —
   **94 for devices, 41 for sites, 59 for prefixes, 54 for IP addresses** [V]. For devices
   that is: `airflow asset_tag cluster* config_template_id console_* contact* created*
description device_bay* device_type* face fields front_port_count has_oob_ip
has_primary_ip has_virtual_device_context id interface* inventory_item* is_full_depth
last_updated latitude limit local_context_data location* longitude mac_address
manufacturer* model modified_by_request module_bay* name offset omit oob_ip_id ordering
owner* parent_bay_id parent_device_id pass_through_ports platform* position power_*
primary_ip4* primary_ip6* q rack_id rear_port_count region* role* serial site*
start status tag* tenant* updated_by_request vc_position vc_priority virtual_chassis*`.
   Still too many to dump raw — step 5 is not optional.
3. **Surface `<name>_id` variants** for FK filters, and prefer them in the description
   (`site_id` takes an integer PK; `site` takes a slug). Both are useful to an agent; the id
   form is what layer 3 will chain from a previous create.
4. **Suppress every `__`-suffixed parameter** from the enumerated list, and instead append a
   single sentence to the tool description explaining the grammar:
   _"Any string filter also accepts `__ic` (contains), `__isw` (starts-with), `__ie` (exact,
   case-insensitive), `__empty`, and a `__n` negation; numeric filters also accept
   `__lt/__lte/__gt/__gte`."_
   This replaces ~230 parameter entries with ~35 tokens.
5. If the surfaced set still exceeds a budget (say 40 entries), rank by: exact-name matches on
   the type's own required create fields first (an agent filtering devices almost always wants
   `site`, `rack`, `role`, `device_type`, `status`, `name`), then FK filters, then the rest,
   and expose the remainder only via a `describe(type, 'filters', contains='...')` search
   parameter on layer 2.

Point 5 is the one that makes the design work: **layer 2 must be queryable, not just
dumpable.** A `describe` that always returns everything about `dcim.device` re-creates the
context problem the 446-tool server has.

**[V — live 4.6.0] The summary is not the valid set, and NetBox will not tell you.** An
unrecognised query parameter is **ignored**: `?nb_mcp_contract_probe=1` returned HTTP 200 and
the same `count` as the unfiltered collection. A model that misspells a filter therefore gets
every object and no signal, which is worse than an error. Two consequences, both load-bearing:

- The execution layer must reject filter names locally, because nothing downstream will.
- It must **not** validate against the summarised list. `name__ic` is legitimate, is one of
  the ~248 names step 4 elides, and is exactly what the grammar sentence tells models to
  write. Validate against the full parameter list (or a known suffix on a known base).

A known filter with a bad **value** needs no local rule: NetBox answers 400 naming the valid
choices (`{"status":["Select a valid choice…"]}`, `{"id":["Enter a whole number."]}`). Only
unknown **names** are silently dropped.

## 5. Size budget

Assumptions: ~3.5 characters per token for schema-ish text; ~4 for prose.

**[X] The 180–220 collection-endpoint estimate was too high.** Measured at NetBox 4.6.7:
**138 collection paths, of which 126 are object types** across `circuits, core, dcim, extras,
ipam, tenancy, users, virtualization, vpn, wireless`. The current hand-written server's 82
endpoints [V] are therefore **65 % coverage, not ~40 %** — a smaller win from generation than
assumed, but the win is in _tool count_, not endpoint count: 446 tools / 82 endpoints = 5.4
tools per endpoint, and full generated coverage would be 126 endpoints × 5 verbs = 630 tools if
built the same way.

| Artefact                                                                        | Composition                                                                                      | Estimate                              |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------- |
| **Raw schema document**                                                         | **12.9 MB JSON, measured, NetBox 4.6.7** [V]                                                     | **≈ 3.7 M tokens — never in context** |
| **Full type registry, keys + verbs only**                                       | **126** × `dcim.device [LGCUD]` ≈ 9 tok                                                          | **~1.1 K tokens**                     |
| **Full type registry, + label from the op-description template (§2.6)**         | 126 × ~22 tok                                                                                    | **~2.8 K tokens**                     |
| **Full type registry, + curated one-line description**                          | 126 × ~38 tok                                                                                    | **~4.8 K tokens**                     |
| **Registry grouped by app, apps expandable**                                    | 10 app lines + 1 app expanded (~25 types)                                                        | **~700 tokens**                       |
| `describe('dcim.device', 'create')`                                             | **30** writable properties × ~22 tok (name, type, required, FK target or enum values) + preamble | **~800–1.0 K tokens**                 |
| …same, if you paste the raw `WritableDeviceWithConfigContextRequest` sub-schema | 30 props × ~90 tok, now inflated further by inline enums and `oneOf` FK unions                   | **~5–8 K tokens**                     |
| `describe('dcim.device', 'list')`, **summarised** per §4.3                      | 6 control + **94** base filters × ~14 tok + suffix-grammar sentence                              | **~1.4–1.6 K tokens**                 |
| …same, **raw parameters array**                                                 | **342 measured** params × ~45 tok                                                                | **~15 K tokens**                      |
| `describe('ipam.ipaddress', 'create')` (a narrow type)                          | ~15 props                                                                                        | **~400 tokens**                       |

**Headline numbers:**

- The full registry with useful labels is **~4–8 K tokens** — affordable once per session, but
  _not_ affordable in every tool description. Ship it behind a `list_types` call (layer 1),
  optionally filtered by app, rather than embedding it in a static tool schema.
- A summarised `describe` is **~1 K tokens**; the unsummarised equivalent is **5–14 K**.
  **Summarisation buys ~10×** and is the difference between the design working and not.
- Budget for a realistic agent session — registry (5 K) + describes for 4 types (4 K) — is
  **~9 K tokens**, versus 446 tool schemas which, at even a conservative 120 tokens each, is
  **~54 K tokens of permanently-resident context**. That is the win, and it is ~6×.

## 6. Risks to the layered design

**Rewritten 2026-08-05 against the real NetBox 4.6.7 document.** Ordered by how likely each is
to actually bite. Three risks got **worse**, four got **better or disappeared**, and **two are
new**. Where a risk moved, it says so.

---

### Got WORSE

**1. You cannot map an object type to its write schema by name — and the wrong name usually
_resolves_. [V, ESCALATED]**

This was risk 1 before and it is still risk 1, but the failure mode is nastier than described.

- **65 of 126** object types have a `Writable<Serializer>Request` write schema — not a handful.
- `dcim.device`'s is `WritableDeviceWithConfigContextRequest`; `DeviceRequest` **does not
  exist**, so a name-mapping rule throws. That is the _lucky_ case.
- `dcim.site`'s is `WritableSiteRequest` — but **`SiteRequest` exists**, as the **bulk-DELETE
  payload**. A name-mapping rule silently returns the wrong schema.
- **46 of the 65 `Writable*`/plain pairs are not identical**, and 8 differ in `required`
  (`WritableCustomFieldRequest` requires `type`; `CustomFieldRequest` does not — likewise
  `action_type`, `version`, `form_factor`, `protocol` ×2, `status`, `role`). So the wrong schema
  is right 95 % of the time and wrong exactly on required-field validation.

**Mitigation (now mandatory, not advisory): resolve by `$ref` from the operation, and add a
build-time assertion that no derived write schema was found by name.** Never parse component
names except to build the `Brief*` reverse index.

---

**2. NEW — the POST request body is a `oneOf`, so the previously-specified pointer walk returns
`undefined` for every object type on NetBox ≥ 4.4. [V]**

```json
"post": { "requestBody": { "content": { "application/json": { "schema": {
  "oneOf": [ {"$ref": ".../WritableSiteRequest"},
             {"type":"array","items":{"$ref": ".../WritableSiteRequest"}} ] } } } } }
```

125 of 126 object types. Upstream has a regression test for it
(`test_post_operation_documents_single_or_array`, refs #20638), so it is permanent. The previous
revision of this document specified `post.requestBody.content['application/json'].schema.$ref`,
which is **`undefined` on every one of them** — the derivation would have produced a registry
with zero create operations, and the failure is silent unless you assert on it.

**Mitigation: unwrap `oneOf[0]` (idempotently — the detail `put` body is a bare `$ref`), and
fail the build loudly if any object type ends up with no write schema.** As a bonus, `oneOf[1]`
gives you documented single-endpoint bulk create for free.

---

**3. NEW — `/api/extras/dashboard/` makes "collection PUT/PATCH/DELETE ⇒ bulk" false. [V]**

`/api/extras/dashboard/` is a 3-segment collection path with `GET/PUT/PATCH/DELETE`, **no
detail path**, and operationIds `extras_dashboard_update` / `_partial_update` / `_destroy` —
singleton operations on the calling user's dashboard taking a single `DashboardRequest`, not an
array. Bulk detection must read the **request body shape** (`type: array`?) or the operationId
suffix (`_bulk_*`?), not the HTTP method. The document contains both cases, so a rule based on
method alone is wrong in both directions.

---

**4. The document is 3× bigger than budgeted. [V, worse]**

Measured **12,938,247 bytes** of JSON at 4.6.7, against an estimate of 4.5–5.2 MB. ≈ 3.7 M
tokens. Streaming-parse it; never buffer it into a string you then hand to anything
model-adjacent. A live `?format=json` fetch is not pretty-printed and should land at 6–9 MB,
but size the buffers for 13 MB. Everything §1.3 and §5 said about never putting this in context
is now understated, not overstated.

---

### Got BETTER, or disappeared

**5. The schema no longer lies about foreign keys. [X — REFUTED, this was risk 5]**

PR #18451 landed. FK write properties are now
`{"oneOf":[{"type":"integer"},{"$ref":".../Brief<X>Request"}]}` — **1329 such properties, and
zero bare `Brief*Request` FK refs**. The nested-object-only form that issue #17709 complained
about is gone at 4.6.7.

**Residual risk, downgraded:** instances on NetBox ≤ 4.3 still emit the nested-only form, so the
FK post-processing must handle **both** shapes and be idempotent. What was a correctness fix is
now a presentation simplification (collapse the union into one line rather than emit a raw
`oneOf` an agent has to reason about).

---

**6. `operationId` collisions are fixed. [X — REFUTED, this was risk 2]**

**Zero duplicate operationIds across 1196 operations; zero `_2`/`_3` suffixes.** NetBox PR
#20407 added explicit `operation_id`s and cleared the `core_background_*` collisions of issue
#20365. The trailing action token is a reliable cross-check today.

**Residual risk:** this was broken as recently as the 4.5 era, so still do not use `operationId`
as the _primary_ key; use it as a cross-check and log disagreement.

---

**7. Enum component names are moot. [X — REFUTED, this was risk 3]**

NetBox sets `'POSTPROCESSING_HOOKS': []`, disabling the enum-hoisting hook. **Zero `*Enum`
components exist.** Enums are inlined with `x-spec-enum-id` (1920 occurrences). `Type666Enum`
et al. cannot occur. Read `prop.enum` directly — no deref, no name to cache.

**Residual risk:** code that _expects_ a `$ref` to a hoisted enum will silently produce no enum
values. Write the reader to handle inline-only.

---

**8. The schema has better labels than assumed. [X — partially refuted, this was risk 6]**

**All 1196 operations have a `description`**, templated as `"Get a list of <verbose name>
objects."`. Parsing that template yields a free, correct, plugin-safe human label for every
type (`users.permission` → "object permission"; `virtualization.interfaces` → "VM interface").

**But the substance of the risk stands.** Component `description` is the serializer docstring
and is boilerplate — one string is repeated 349 times. A label is not semantics; "Device" does
not tell a model when to choose a device over a virtual machine. **Still plan a curated
one-liner table for the top ~40 types** — but as an enrichment over a decent generated label,
not as the whole labelling strategy. Scope of hand-written content: reduced.

---

### Unchanged or refined

**9. Some collection paths are not object types — and the previously-specified guard does not
catch them. [V, refined]**

The old guard ("only emit a type when a collection `get` exists") discards **zero** paths: all
138 collections have a `get`. The working rule is **`post` on the collection AND a matching
`/{id}/` detail path** ⇒ **126 types**, excluding exactly 12: `core/background-queues`,
`core/background-workers`, `core/background-tasks`, `core/data-files`, `core/jobs`,
`core/object-changes`, `core/object-types`, `dcim/cable-terminations`, `dcim/connected-device`,
`extras/tagged-objects`, `users/config`, `extras/dashboard`. Full enumeration of every
non-object-type path, including the 32 sub-resource actions, is in **§2.7** — use that list, do
not re-derive it by hand.

Several of the 12 are genuinely useful read-only endpoints (`core/object-changes` is the
changelog; `core/jobs` is job status). **Model them as a distinct "read-only pseudo-type" with
list+get only**, rather than dropping them.

**10. Some object types have no describable create. [V, narrowed]**

Exactly **one** — `/api/extras/scripts/` has a `POST` with no `application/json` request body.
Plus the `core/background-*` viewsets, which have no serializer at all and now live outside the
type set anyway (see §2.7). The mitigation is unchanged and cheap: tolerate a path item with no
resolvable schema, mark the operation `describe`-unavailable, and count it in the build
diagnostic.

**11. Response `required` does not mean create-required. [V, NEW nuance, replaces an incorrect
claim]**

`COMPONENT_NO_READ_ONLY_REQUIRED` is **not** set at 4.6.7 (the previous revision said it was).
`DeviceWithConfigContext.required` has 22 entries including `id`, `url`, `created`,
`last_updated` and nine `*_count` fields. **Only the write component's `required` is
create-required** (`WritableDeviceWithConfigContextRequest.required = ["device_type","role",
"site"]` — three fields, not twenty-two). Reading `required` off the wrong component would tell
an agent it must supply `id` to create a device.

**12. Choice fields are asymmetric between read and write. [V, confirmed and sharpened]**

Write: bare string with inline `enum`. Read: `{"type":"object","properties":{"value":{enum…},
"label":{enum…}}}` — two parallel enums. Agents that echo a read response back into an update
will send `{"value": "active"}` and get a 400. Layer 2 must describe the two forms separately.

**13. Filter counts are as bad as feared. [V]**

**342 parameters on `GET /api/dcim/devices/`, 72.5 % of them `__`-suffixed. 361 on
`/api/dcim/interfaces/`. 15,832 across the document.** Dumping them is ~15 K tokens for one
call. §4.3's summarisation rule is not an optimisation, it is load-bearing — and note the base
set for devices is **94**, above the 40-entry budget §4.3 point 5 assumes, so the ranked/queryable
`describe` is required for devices specifically, not just for pathological types. Also add
`__regex`, `__iregex` and `__any` to the documented suffix grammar; the previous revision missed
all three.

**14. Slug ≠ model name. [V, confirmed]**

`/api/users/permissions/` → `ObjectPermission`; `/api/extras/tagged-objects/` → `TaggedItem`;
`/api/virtualization/interfaces/` → `VMInterface`; `/api/dcim/virtual-chassis/` is already
singular in the URL. Do not claim the derived key equals Django's `app_label.model_name`
(§2.3).

**15. Schema generation is expensive and happens per request. [V, unchanged]**

netbox issue #6423 is open. A cold start that fetches ~13 MB and waits seconds is a bad first
impression. Persist the derived registry keyed on `netbox-version` + plugin set; ship a
pre-derived registry (the committed fixture's provenance format is a good template) as a warm
start.

**16. `netbox-version` can be `null`. [V, unchanged]**

netbox-docker issue #1582. Fall back to hashing the schema body while streaming.

---

### Still completely unverified

**17. Plugins. [I — and the gap is now explicit]**

**`/api/plugins/**` appears nowhere in the 4.6.7 document**, because NetBox generates
`contrib/openapi.json` from a stock instance with no plugins installed. Every plugin claim in
this spec — the `/api/plugins/<plugin>/<model>/` path shape, the 4-segment collection rule, the
absence of `Brief*`/`Writable*` conventions in third-party serializers, name collisions between
plugins — is **untested and untestable from the committed fixture**.

This is the largest remaining hole, and it matters: the target deployment uses
`netbox-inventory`. **Before shipping, fetch a schema from an instance with the plugins actually
in use and re-run the §2.2 classification and §3.1 pointer walk against it.** Namespace plugin
types as `plugins.<plugin>.<model>` and treat FK-resolution failures inside plugin schemas as
normal.

**18. Version drift in the derivation rules themselves. [V, and this document is Exhibit A]**

Between 4.1 and 4.6, NetBox changed: FK write shape (nested → `integer | Brief`), POST body
shape (`$ref` → `oneOf`), enum handling (hoisted components → inlined), operationId uniqueness
(colliding → unique), `COMPONENT_NO_READ_ONLY_REQUIRED` (on → removed), and singular vs bulk
semantics on collection paths. **Six of the rules in the previous revision of this document were
wrong for 4.6.7, and four of them would have failed silently.** Rules verified at 4.6.7 will not
hold at 4.8.

**Mitigation, and it is the single most important structural recommendation here: the
derivation layer must self-audit and refuse to ship a degraded registry.** On every build,
assert and report:

```
N paths total, M classified as object types
0 object types with no resolvable write schema        (expect exactly 1: extras/scripts)
0 object types with no resolvable patch schema
0 object types with no resolvable read schema
0 write schemas resolved by name rather than by $ref  (must be 0)
0 unclassified /api/ paths not in the known-exception list
X FK properties, of which Y matched a known FK shape  (Y/X must be ~1.0)
```

and fail loudly on a diagnostic rather than producing a thinner registry. **Every single one of
the four silent failures found in this pass would have been caught by that block.**
