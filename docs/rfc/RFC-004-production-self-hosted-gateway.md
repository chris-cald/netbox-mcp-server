# RFC-004: Production self-hosted gateway

**Status:** Proposed

## Decision

The production gateway will retain schema-derived resource CRUD and, in a later
phase, add exactly one generic semantic-operation tool: `netbox_invoke`. It
will not add object-specific action tools. This RFC defines boundaries and
validation gates; it does not implement HTTP, OIDC, actions, bulk writes, or
container deployment. M2 implements the server-side token-file credential
source described below without adding another transport or MCP tool.

## Why one generic invocation tool

The existing five CRUD/discovery tools plus `netbox_invoke` form the six-tool static MCP surface. `netbox_read` and
`netbox_write` address schema-derived resource CRUD: list/get/create/update/
delete on a collection resolved from the connected instance's OpenAPI schema.
They remain the right interface for records and retain local field validation,
endpoint safety, pagination, and delete confirmation.

Semantic actions are different. They represent named business operations such
as a workflow trigger, a device lifecycle action, or a plugin-provided task;
they are not a second spelling of arbitrary REST access. Adding a tool per
action would make the static tool list version- and plugin-dependent, consume
context, and make host authorization prompts inconsistent. Instead,
`netbox_invoke` will receive an operation identifier and a structured input.
The identifier must resolve in the server-owned registry; callers never supply
a URL, method, or endpoint. Resource CRUD stays in the existing tools, and
semantic actions use `netbox_invoke` only when the registry declares them.

## OperationRegistry

A server-owned `OperationRegistry` will be built from approved core operations
and discovered capabilities only after each entry has passed its validation
gate. Each entry must contain at least:

- stable operation id and human title;
- input and result schemas, plus a request adapter that has no caller-supplied
  URL or HTTP method;
- an authorization classification: `read`, `write`, or `destructive`;
- idempotency and audit metadata, including the target resource type where
  applicable;
- availability/version constraints and a user-safe unavailable explanation.

The gateway authorizes before dispatch using this classification and the
identity's policy. `read` may retrieve data, `write` may create or mutate
state, and `destructive` requires the strongest confirmation/policy path.
NetBox remains the final authority for its own token permissions. Registry
entries cannot elevate a NetBox credential or bypass its response. Unknown,
disabled, or unavailable operation ids fail locally and are not proxied.

## Bulk writes

Bulk mutation is a closed schema-derived collection operation, not an
unconstrained array. `netbox_write` exposes only `bulk_create` (POST),
`bulk_update` (PATCH), and `bulk_delete` (DELETE) when the connected OpenAPI
document proves the collection path, JSON-array request, exact method, and
success response. It locally validates every item, caps a request at 100 items
and 25 KiB UTF-8 JSON, and sends it once with no automatic retry.

Bulk update and delete first refuse and issue an in-memory random token bound
to the exact operation, object type, and canonical payload. The token expires
in five minutes, is consumed before dispatch (including a failed dispatch), and
cannot authorize a changed payload or retry. This is a human-confirmation gate,
not an authorization boundary; the NetBox token remains authoritative.

## Transport and credentials

Stdio remains the default transport and exactly six tools are registered in
this M3a milestone. A later Streamable HTTP host will construct an isolated server
per authenticated request/session boundary and inject a server-scoped NetBox
API dependency. It must not share a process-global client across tenants or
credential sources.

OIDC authenticates the gateway caller; it is not forwarded to NetBox as a
substitute for NetBox credentials. Gateway authentication, authorization, and
audit identity are separate from NetBox API credentials. M2 token-file support
is server-side only: exactly one of `NETBOX_TOKEN` and `NETBOX_TOKEN_FILE` is
accepted. The file source must be a readable regular file; it is read before
every NetBox request so rotation takes effect without restarting the server.
File locations, contents, bearer values, and NetBox tokens must never appear
in tool arguments, tool results, logs, errors, URLs, or client configuration
generated by the gateway. Missing, unreadable, non-file, and empty sources
fail closed. Deployment configuration likewise remains outside the MCP
caller's control.

## Phased rollout and validation gates

1. **M1 dependency seam:** establish an injected, narrow collection-relative
   NetBox API dependency while preserving stdio behavior, lazy schema loading,
   and current CRUD/delete guards.
2. **M2 credentials (implemented):** validate mutually exclusive inline/file
   configuration, regular-file/readability and empty-content failures,
   rotation behavior, and redaction tests. Do not expose credentials to MCP.
3. **M3 HTTP/OIDC:** validate the installed MCP SDK's Streamable HTTP API,
   session lifecycle, OIDC issuer/audience/claim policy, CSRF/origin policy,
   rate limits, audit events, and tenant isolation against supported versions.
4. **M3a/M3b registry/actions (implemented):** a closed registry validates
   schema-confirmed native IPAM prefix availability GET/POST and DCIM interface
   trace/front-port/rear-port path GET detail actions, their action-specific
   inputs, target type, and read/write classification before dispatch. Other
   actions remain deferred.
5. **M4 bulk (implemented):** exercise isolated native collection POST/PATCH/
   DELETE, persisted state, schema validation, limits, and one-use confirmation
   grants against the disposable fixture. Atomicity and partial-failure semantics
   remain NetBox-owned and are surfaced without retries.

NetBox's action endpoints, plugin discovery shape, supported version matrix,
Streamable HTTP SDK details, and OIDC deployment requirements are deliberately
validation gates rather than assumed facts. No operation is enabled merely
because a similar endpoint appears to exist in another NetBox release.
